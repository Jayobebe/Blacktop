# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project overview

"Blacktop" (repo name `convoy-comms`) is a ride companion app for motorcycles, cars, bicycles, e-bikes and e-scooters: ride tracking and stats, GPS-synced convoys, in-ride voice chat, crash/rescue detection, an in-app map with turn-by-turn, a vehicle garage and logbook, plus opt-in community features (Blacktop World, crews, cards, arcade). Onboarding personalises the whole app to the rider (see "Personalisation" below). It's a Vite + React + TypeScript SPA wrapped with Capacitor for iOS/Android, backed by Supabase (Postgres, Auth, Realtime, Edge Functions). The project originates from and is synced with Lovable (`lovable-tagger` dev plugin, `.lovable/` folder) — changes pushed here also flow back into the Lovable project.

## Commands

```sh
npm run dev        # Vite dev server on port 8080
npm run build      # production build
npm run build:dev  # build in development mode (used for preview/debug builds)
npm run preview    # preview a production build
npm run lint        # eslint .
npm run cardwars:check    # Card Wars rules: matchmaking, prizes, dog tags (CW_RULES=2 for the newer rule set)
npm run cardwars:balance  # Card Wars ratings and prices (-- --check: catalog.ts in step?)
```

There is no test suite and no `tsc --noEmit`-style typecheck script configured — `npm run lint` and `npm run build` are the main correctness checks. TypeScript has `strictNullChecks` on (both tsconfigs); the rest of `strict` (`noImplicitAny`, `noUnusedLocals` etc.) is off. `npx tsc -p tsconfig.app.json --noEmit` must stay at zero errors: Vite builds without type-checking, so nothing else catches a regression. Peaks that can be hidden are typed `number | null` (`ConvoyMemberInfo.topSpeed`, card stats, logbook rides): handle the null as "--".

The native shells live in `android/` and `ios/` (Capacitor 8; iOS uses Swift Package Manager, no CocoaPods; building iOS needs a Mac, see `ios-setup.md`). `capacitor.config.ts` points both at the deployed web app (`server.url`), not a local dev server, so only native changes need a new app build. App icons and splash screens for both platforms come from `public/apple-touch-icon.png` via `python scripts/make-app-icons.py` (Pillow). Android release builds sign with `android/keystore.properties` (git-ignored; see `keystore.properties.example`). Two syncs: `npm run cap:sync` (the shells load the live site, for testing on a phone) and `npm run cap:sync:store` (builds, then syncs with `CAP_BUNDLED=1`, which drops `server.url` so the app's own `dist` is bundled and a cold start works offline: the store build). Never bare `npx cap sync`: on Windows the CLI writes the iOS `Package.swift` plugin paths with backslashes, and `scripts/fix-ios-spm.mjs` puts them right. `lib/platform.ts` is where web and native differ (the web answers exactly as before): `isNativeApp()`; `shareOrigin()` (links others open use `https://blacktoplive.com` in the app, never its own `localhost` origin); `paymentsAvailable()` (crypto payments, i.e. Pay Up tips, Blacktank, `/pay`, the Pay Up welcome card and demo slide, are web and Nimiq mini app only, since the stores don't allow them). `place-search` and `what3words` already allow the app origins (`https://localhost`, `capacitor://localhost`); the other functions allow any origin. Native-only behaviour, all no-ops on the web:
- Ride GPS keeps going with the screen locked (`ride/lib/backgroundGps.ts`, @capacitor-community/background-geolocation): Android runs a location foreground service with a "Ride in progress" notification (so no `ACCESS_BACKGROUND_LOCATION`; `android.useLegacyBridge` keeps updates coming past 5 minutes), iOS the `location` background mode. Only between start / resume and pause / end; Track Pack's high rate keeps @capacitor/geolocation.
- Speech goes through the phone's TTS engine (@capacitor-community/text-to-speech in `map/lib/speech.ts`; Android's WebView has no Web Speech).
- `components/NativeBridge.tsx`: Android back closes a dialog / the radio / the map, then goes back, and from Home backgrounds the app (never while the alarm is armed); `appUrlOpen` routes blacktoplive.com links (Android intent filter with `autoVerify`; it needs `/.well-known/assetlinks.json` with the Play signing key's SHA-256 on the site, and iOS needs the Associated Domains capability plus `apple-app-site-association`).
- Files the app makes (receipts, recap cards, GPX / CSV, videos) open the share sheet (`lib/nativeShare.ts`, written to the cache in chunks); the overlay video is only cleared once shared.
- Push: `notifications/lib/nativePush.ts` registers the phone's token as endpoint `fcm:<token>` / `apns:<token>` in `push_subscriptions` (migration `20261006000000_native_push.sql` widens `is_push_service_endpoint`), so crews, nearby riders and weather target it like any device; that migration's patterns used repeat counts over Postgres's limit of 255 (`{20,1000}`), which made the check raise 2201B for every device, browsers included, until `20261018000000_push_endpoint_check.sql` (lengths by `length()`, never a big `{n,m}` in a Postgres regex); `send-push/native.ts` delivers by FCM HTTP v1 / APNs (secrets `FCM_SERVICE_ACCOUNT`; `APNS_KEY_ID`, `APNS_TEAM_ID`, `APNS_PRIVATE_KEY`, `APNS_BUNDLE_ID`, `APNS_SANDBOX`) and skips native devices without them. Android channels `rescue` (loud) and `general`. Built in only with `VITE_NATIVE_PUSH=1` at build time (registering without `android/app/google-services.json` crashes Android); without it Settings shows notifications as unavailable in the app.

Supabase Edge Functions live in `supabase/functions/*` and are deployed via the Supabase CLI, not via npm scripts. Every function has an entry in `supabase/config.toml`; all use `verify_jwt = true` except `send-push` (called by the database; rider actions check the session in code). Add a config entry when you add a function. Migrations go out later than the app (through Lovable), so UI for a new server feature is gated on `useServerCap` / `hasServerCap` (`lib/serverCaps.ts`): each cap is probed once per launch with a harmless read RPC (PGRST202 = not deployed yet, any other answer = there; offline keeps the stored answer, never seen = off, demo mode = on). Add a probe there when a feature depends on a new migration.

## Architecture

### Feature-based organization

Code is split between generic `src/components`, `src/hooks`, `src/lib`, `src/pages` and domain features under `src/features/<feature>/`, each with its own `components/`, `hooks/`, `lib/`, `types.ts`, and a barrel `index.ts` that defines the feature's public surface. Other features and pages should import from a feature's `index.ts`, not reach into its internals. Current features: `alarm`, `convoy`, `ride`, `voice`, `rescue`, `waypoints`, `garage`, `cards`, `profile`, `settings`, `proximity`, `pillion`, `logbook`, `track`, `notifications`, `speedshop`, `map`, `crew`, `blacktank`, `arcade`, `card-wars`, `radio`, `experience`, `tips`, `hazards`, `enterprise`, `stickers`, `guide`, `integrations/discord`.

`src/pages/*` are route-level screens composed from features; routing lives in `src/App.tsx`. Home, onboarding, the lobbies, the ride and pillion screens load eagerly; every other screen (and the map overlay) is a `lazyPage()` that's prefetched once the app is idle, so it still opens offline. Keep heavy dependencies (MapLibre, ffmpeg) out of anything the eager screens import (Home loads the globe and the Enterprise cards lazily, imports `useEnterprise` and `racerPhase` straight from their files, and App imports `EnterpriseSync` from its file: a feature barrel there pulled ~190 KB into the first load): a barrel that re-exports a heavy component drags it into the first load, which is why the Track Day screens live in `@/features/track/views`, not `@/features/track`.

### Global client state via module-level stores, not Context

Cross-cutting state (e.g. convoy state in `src/features/convoy/hooks/useConvoyState.ts`) is implemented as a module-level singleton object + `Set` of listener callbacks, exposed to components through `useSyncExternalStore`. This is the established pattern for shared state in this codebase — prefer it over introducing new React Context providers or a state library. Profile/settings (`useProfile`, `useSettings`) follow the same pattern and are read at the top of `App.tsx` to gate routing (onboarding vs. main app) and to initialize the accent color. `useProfile` must stay one store: when each caller kept its own copy, the gate never saw the new profile after sign-up and riders were stuck on the name step.

Server data fetching/caching uses `@tanstack/react-query` (`QueryClient` set up in `App.tsx`).

### Realtime: Supabase Postgres + Realtime channels, WebRTC for voice

- Convoy membership/destination/waypoints are rows in Postgres (`convoys`, `convoy_members`, ...) read/written via `supabase.from(...)`, with the active convoy id cached in `localStorage` (`blacktop_active_convoy_id`) so a reload can restore session state.
- Ephemeral, low-latency events (rescue pings, lobby chat, live stats) go over `supabase.channel(...)` broadcast channels scoped per convoy (e.g. `rescue-${convoyId}`), not the database.
- Voice chat (`src/features/voice/hooks/useVoiceChannel.ts`) is WebRTC, using a Supabase Realtime channel purely as the signaling transport. ICE servers come from `voice/lib/iceServers.ts`: public STUN plus short-lived TURN credentials from the `turn-credentials` Edge Function (Cloudflare Realtime TURN; secrets `CLOUDFLARE_TURN_KEY_ID`, `CLOUDFLARE_TURN_API_TOKEN`). Without TURN, riders on mobile data usually can't hear each other, so the app warns once when no relay is available. It's a full mesh (every phone sends to every other), so voice takes `VOICE_MAX` (8) riders and no more, while the convoy itself stays unlimited: every phone works out the same slots from the channel's presence (`voiceSlots`: the leader first, then whoever joined voice earliest), a rider past the line waits with no audio links and is let in when someone leaves, and signalling to or from a rider without a slot is ignored. Untested with real phones. Speaking indicators are broadcast over Realtime and prove nothing about the audio path; `peerLinks` in the hook tracks real per-peer audio links and the ride member list shows "No audio link" when one is down. iOS/Safari needs special handling: audio must be "unlocked" via a user gesture (`unlockIOSAudio`) before `AudioContext`/playback will work, and audio constraints differ (no fixed `sampleRate`). Android routes to Bluetooth headsets/intercoms through the native `NativeAudioRoutePlugin` (`voice/lib/nativeAudioRoute.ts`). Voice-recording consent (mixing convoy voice into a rider's overlay video) requires both `voiceRecordingEnabled` and `rideOverlayEnabled`.

### Map and routing

`src/features/map` is the in-app map (MapLibre, `BlacktopMap` / `BlacktopMapOverlay`): place search, multi-stop routes, a direct-vs-twisty route choice (`RouteOptions`), a round-trip loop generator with Twisty/Scenic/Relaxed styles (`LoopPlannerPanel`), offline map packs (`OfflinePacksPanel`, `tileCache`), a rain radar overlay, a weather detour offer (`weatherRoute`), speed cameras and POIs. All routing, search and Overpass calls go through the `place-search` Edge Function (`kind`: `route`, `twisty`, `loop`, `search`, `reverse`, `cameras`, `overpass`, `roads`), which proxies OSRM, Valhalla, Nominatim-style search and Overpass; the client only ever sends coordinates (plus the rider's route preferences and vehicle, `routePrefs()` in `lib/routing.ts`).

- Own geo server: `infra/geo` (Docker: Valhalla, OSRM, Photon, Overpass, Open-Meteo behind Caddy with a bearer token; `build-valhalla.sh`, `build-osrm.sh`, `get-photon.sh`, weekly `update.sh`; the README has the setup and sizing). Every outside call from the Edge Functions goes through `_shared/upstream.ts` (`viaGeo(service, publicBases, call)`): with the `GEO_SERVER_URL` and `GEO_SERVER_TOKEN` secrets set it tries our server's `/<service>` first, falls back to the public service on failure and rests ours for that service for a minute; without them it calls the public services exactly as before (`hasOwnGeoServer` is false and nothing changes). With the server: routing is engine `both` (`PLAN` in `place-search`): Valhalla routes, and twisty / loop planning tries every candidate on both engines, scores them all on Valhalla road data and keeps the best; search and reverse come from Photon in Nominatim's shape (`photonForSearch` / `photonReverse`, no Nominatim); weather alerts in `send-push` use its Open-Meteo (`OWN_WEATHER_MODEL`); and every `route` answer carries `durationRange` (OSRM timed alongside, same roads only), which the app shows as ETA and time-left windows ("12:44–13:05", `map/lib/eta.ts`: `TurnBanner`, the destination card, `ConvoyStatusBar`). Without it none of that appears. Route weather on the phone still calls Open-Meteo directly (per-phone limits).
- Routing code lives in `place-search/routing.ts` (engines, road data, scoring, planners) so `npm run routing:eval` (scripts/eval-routing.ts) can compare OSRM, Valhalla and both on the same trips, judged on Valhalla road data (throttled against the public servers; `--only=`, `--engine=`). Valhalla road data comes from `trace_attributes` (`walk_or_snap`): road class, speed, built-up density (town from 9 of 15), roundabouts, slip roads, surface. It's only fetched with our own server; on the public servers Valhalla routes score as open road, as they always have. Valhalla's small-road times are cautious, so its twisty detours are capped on distance (1.6x) with a loose time cap (2.5x); OSRM keeps its 1.6x time cap.
- Engines: the public OSRM demo by default. It ignores `exclude`, so when the rider has a route preference on (Settings → Navigation → Route Preferences: avoid motorways / tolls / ferries / unpaved; `navAvoid*` settings) or rides a bicycle / e-bike / e-scooter, routes go to Valhalla's public FOSSGIS server (`motorcycle` / `auto` / `bicycle` costing, soft `use_*: 0` avoidance, `format: "osrm"` so steps parse the same) with OSRM as the fallback (`routeFor` in the function). Twisty and loop candidates use the same router the app will ride, so what's scored is what's ridden.
- Twisty and loops score real bends, not junctions (`analyseRoute`): the line is resampled every 25 m, turning per step is capped (junctions and roundabouts barely count), weighted by road type (from OSRM's per-segment speed, or Valhalla's road class and density with the geo server: full on secondary roads, well on tertiary, little on estates / lanes, ~nothing on dual carriageways), with heavy penalties for spurs ridden back along and U-turns at vias. Loops run two rounds, re-scaling the ring to land on the asked length; scenic loops route through real viewpoints / peaks / waterfalls (Overpass) and name them; relaxed means flowing quiet roads, not the straightest. A twisty A→B can be one bend or an S (`vias`, both lobbies ride them as "Twisty leg" stops / waypoints). Solo routes live in the `soloRoute` store; convoy routes come from convoy waypoints.

The dark basemap is OpenFreeMap's with the contrast lifted (`lib/basemapContrast.ts`); load it through `loadDarkMapStyle()` (`lib/darkStyle.ts`) in any map with the real-world dark look (the Blacktop map, ride flyovers) so they match. The map opens at the rider's last known position (`lib/lastView.ts`), not London. Water is drawn as the backdrop's BLACKTOP wordmark in a faint accent tint (`lib/waterWordmark.ts`, a static `fill-pattern`). Card drops (`useCardDrops`) are a map layer like the hazard pins (`lib/cardDropLayer.ts`, one sprite per look: edge / glow / count badge) with the same rule: from zoom 9, full size at 14, off during rides. A refetch only swaps the layer's data (DOM markers rebuilt on every refetch and blinked). Pins (`lib/mapPins.ts`): nearby places come straight from the basemap tiles' `poi` layer (no requests; fewer when zoomed out, by the tiles' rank), plus saved places and recent destinations; category colour + the style's icon recoloured white; hidden while the rider is moving. With no route, panning the map turns off the snap-back to the rider until the locate button is tapped (`freePanRef`). Tapping a pin orbits the camera round it (GPS follow holds off via `orbitingRef`) with Back / Navigate; Navigate goes straight to the follow view on the rider (`followRider`), with no trip overview first (two competing camera moves made it bounce). Phones in landscape use the `short:` Tailwind screen (`tailwind.config.ts`): narrow search, chips only while searching, no zoom buttons, bottom cards and the speed card in a left-hand column. MapLibre's own geolocate dot is off (Blacktop draws the rider marker) and the compass doesn't visualise pitch. The map overlay reports `ready` after its first full draw (or 6 s): until then the app backdrop is the loading screen. The overlay stays mounted while hidden, so closing the home map (the X or the inactivity auto-close; not during a ride, not from a lobby) bumps `resetSeq` (`resetBlacktopMap`) and the map ends its route, guidance, speech and any pin orbit; a ride's route ends with the ride.

MapLibre is v6 (ESM only): `import * as maplibregl from 'maplibre-gl'` (no default export), and any file that creates a map also imports `@/lib/maplibreWorker`, which points MapLibre at the worker Vite builds (without it the map stays blank in production). Missing style images are supplied with `map.setMissingStyleImageResolver`; the `styleimagemissing` event can't add them any more.

Adding sources/layers: use `lib/whenStyleReady.ts`, never `isStyleLoaded()` + `map.once('load')`. `isStyleLoaded()` is false whenever tiles are loading (constantly mid-ride) and `load` fires only once, so layers added later never drew.

Routing failures degrade calmly: route requests time out after 15 s, set `routingStatus` offline, and the map keeps the last line, shows "Offline — following GPS track" under the turn banner and retries with backoff (15 s, 30 s, 1 min, then every 2 min; straight away on the browser's `online` event). Turn-by-turn: `BlacktopMap` asks for the route with `steps: true` (OSRM manoeuvres per leg) once from the rider's position, then only re-plans when the stops change, the rider is off the line (`useTurnByTurn`: >45 m for 4 s, at most every 12 s) or a request failed. While navigating the follow camera holds the rider's own zoom: a zoom they make themselves (`zoomend` with an `originalEvent`, not while orbiting a pin) with a destination set is saved as `blacktop_nav_zoom` (12–19) and used for every follow, resume and route-drawn camera; without a destination it only ever nudges in. Don't reintroduce polling: the router is the public OSRM demo server behind a 60 req/min per-rider limit. `lib/navigation.ts` places manoeuvres on the line, matches GPS fixes to it (windowed so loops don't jump to the finish) and writes the instructions; `lib/speech.ts` speaks them (Web Speech, unlocked on the first tap for iOS) when the `navVoiceEnabled` setting is on (`navVoiceStyle`: standard = the phone's plain voice; cockpit / rally = radio treatment, rally adds pacenotes from `lib/pacenotes.ts`), and `src/lib/audioDuck.ts` lowers voice chat and Blacktop Radio while it talks. `TurnBanner` takes the search bar's slot at the top of the map while guiding (for any guided route; it shows "Follow the route" when the router returned no manoeuvres), stays up regardless of the voice setting, and replaces the bottom destination card (destination, time/distance left, ETA, leader Skip). Its X ends a solo route, or just this rider's directions in a convoy; the destination card's Go button starts guidance before moving. Its bottom row has Share ETA ("Riding to … 12 mi to go, ETA 14:05" through the share sheet, `lib/shareText.ts`; nothing goes through the server) and, when the rider's preferred nav app (Settings → Navigation) isn't Blacktop, Open in Google Maps / Apple Maps / Waze (`lib/navHandoff.ts`); Blacktop keeps running underneath. Passed solo stops and weather detours drop off the plan; a convoy leader reaching the current waypoint completes it. `useNavigation.openNavigation` uses the same hand-off; the ride screen's map button always opens the Blacktop map (most riders keep the default Google preference and ride on it).

### Track Day builder (`src/features/track`)

Tracks (`TrackDef`: start/finish gate, sector split gates in running order, `outline` = the lap starting at the start/finish) come from the circuit library or a GPS lap, both ending in `ChaseCamPlacer` (picking roads on the map was dropped: the public Overpass servers it needed timed out too often; tracks built with it still work, and ones saved before outlines can't be re-edited):

- GPS: `startWalk` records until `LoopCloser` (`lib/walker.ts`) sees the trail come back onto itself heading the same way (so hairpins and figure-of-eight crossovers don't count), or the rider finishes by hand; the smoothed lap is `walkLoop`.
- Library: `npm run tracks:build` (scripts/build-circuit-library.ts) turns every OpenStreetMap circuit relation (`type=circuit`, one per layout) into a lap through the same `roadLoop` code and writes static files to `public/circuits/` (`index.json` + `<relation id>.json`), so search (`TrackSearch`, `lib/circuitLibrary.ts`) is instant and offline. Search shows venues (`venuesOf`: layouts within 2.5 km, named by their shared words); one with several layouts opens to pick one (`layoutLabel`: "Grand Prix", "Indy") and nothing hits Overpass at runtime. A lap never includes a pit lane: ways with a pit role, or named / tagged as one (`PIT` in `roadLoop.ts`: "Pit Lane", "Pits", "Pit Entry", not "Pit Straight"), are dropped; a layout whose own ways only close through the pits borrows its venue's other track (`lapWithVenue`, e.g. Brands Hatch Indy from the GP layout), and one that still can't close without them, or whose lap misses most of its mapped track (< 60 %), is left out (the build lists why). Each layout is built from the ways of its own download (a way fetched again later may have been redrawn). Direction comes from how the ways are drawn; start/finish and sectors are never imported (the only open sector data, lovely-track-data, is non-commercial): the racer places them in the chase cam. The files are ODbL: keep the "© OpenStreetMap contributors" credit and keep them openly available. The script caches Overpass answers in `node_modules/.cache/circuit-library` and resumes; `-- --fresh` re-downloads.
- `ChaseCamPlacer` runs a camera round the lap (chase / bird's-eye / whole lap; play, pause, rewind, speed, scrub, reverse direction). Markers are distances along `lib/centerline.ts`'s `Centerline`, so gates are always on the lap and square to it; sectors fill themselves in from start/finish round to start/finish. `TrackEditor` routes between them and re-opens saved tracks on their outline.
- Home (`TrackHome`) is the same for both roles: search, a GPS lap (`WalkScreen`; the racer rides it, the pit crew may walk it), the scanner for the other side's QR, the selected track and the shelves; only the QR wording and the main button differ (racer: Ready up; pit crew: Show racer QR).
- Pairing (`lib/link.ts`), either way round: the racer shows their QR (`BTTRK1:`) and the pit crew scans it, or the pit crew picks a track and shows theirs (`BTTRKP1:`); the racer scans it (Scan pit crew QR, `joinPitLink`) and is sent the track (`track` message, checked by `cleanTrack`, saved and selected). Older apps ignore `track` and can't read a pit QR, so they keep pairing the first way.
- Pit lane timing (`lib/pits.ts`, `lib/pitLanes.ts`): library layouts carry their pit lanes (`pits` in the circuit files; a layout without one borrows its venue's), and a GPS lap at a real circuit borrows the nearest venue's. On save, `withPits` puts pit-in / pit-out lines across the pit lane itself (set back from where it meets the track, at least 6 m clear of the racing line, crossed with only a 2 m margin, so riders staying out never trip them) and `startFinishPits` (the start/finish carried across the pit lane, drawn thin on the minimap) so laps through the pits still count. `PitTracker` follows a visit: lane time, each stop in the box (GPS near zero confirmed by the phone's dynamic G, since GPS speed jitters at rest), the braking point before it and the launch out of it (a G spike), time over the limit. The crew sets the limit (`pitLimit` message; 60 km/h / 40 mph by default) and both phones show `PitLaneCard` (speed green / amber / red against it). Laps that go in or out are `pit: 'in' | 'out' | 'inout'`, not valid (never a best, sector or delta reference), counted in the total; a launch in the pit lane starts the session in it. Sessions keep `pitStops`; at the end the racer sends the whole session to the crew (`session` parts, `parseCrewSession`), whose results card has the pit stops and a 3D flyover (the ride flyover, lazy-loaded). Tested by simulation on every library circuit with a pit lane: no false pit entries on any racing line.
- Readying up doesn't start launch detection: the racer first heads to the grid (riding out of the pits can't start the clock), then taps I'm in position (`confirmInPosition`, `inPosition` in the snapshot, which the pit crew sees); the rolling-start button works either way.
- Track Day home (`TrackHome` in `RacerView` / `PitView`): search, the GPS lap and scan buttons, the selected track (sent to the pit crew as soon as it's picked, `selectTrack`) with Ready up (arms timing; the launch starts it), then three horizontally scrolling shelves: Previous (by `lastUsedAt`/sessions), Custom (built by the racer) and Favourite (starred). Pit board calls and rider calls are spoken as well as shown (`lib/pitCalls.ts`, via the map's `speak`, which ducks voice chat and radio).
- Post-race telemetry is the pit crew's call (`lib/postRace.ts`, `PostRacePicker`): picking or saving a track on the crew's phone asks for Results (the session is sent to the crew at the end), 3D flyover (plays as the results open, both phones) and Overlay video (the racer's phone runs `useLiveOverlayRecorder` from the launch, saves it with the session's ride and offers it from History). It goes to the racer as a `postRace` link message, only before timing; without a crew choice the overlay follows the racer's `rideOverlayEnabled`.
- Track records (opt-in, `trackLeaderboardsEnabled`, the switch under Track Day in Settings → Your Blacktop; migration `20261008000000_track_records.sql`): ending a session on a library layout (`osmId`) submits the fastest clean lap (`recordLap`: valid, no pit, good GPS) with `submit_track_lap` per layout, direction (`lapDirection`) and vehicle class; it rejects laps over 350 km/h average, laps whose sectors don't add up to them and laps without the GPS behind them (`_fixes` under 0.8 a second or `_max_gap_ms` over 3 s, from `lapEvidence`; `recordLap` only offers laps that pass), keeps a lap under 90 % of the board's median (5+ riders) `flagged` (shown only to its rider, beats nobody), and returns every rival beaten at their current time once. Each one beaten gives their card as a dog tag (a Spectre, `earnSpectre` with `track`) and 3 Speed Demon badges on the receipt, and pushes them `track_beaten`. `TrackBoard` shows the board under the selected track; turning the switch off calls `leave_track_leaderboards`. Custom tracks never have boards. There are no time attacks on public roads any more (card challenges, their table and the map's challenge UI were removed); Spectres earned from them stay in the vault. Track Day receipts and History chips are pink (`.receipt-track`) and print theoretical best, pit stops, fastest pit, board position and dog tags.

### App audio

Everything the app says or beeps sounds like a fighter-pilot radio (`lib/radioFx.ts`): squelch key-up and release, a static bed under speech, cockpit warning tones (`warningTone`: speed camera, ANPR, crash-check master caution), all through one comms-band chain. `speak()` is a radio call by default; turn-by-turn passes `kind: 'nav'` and follows the rider's voice style (standard stays plain). Radio calls go out in the pilot voice when it's downloaded (`lib/pilotVoice`): a male Piper neural voice per language (`voices.ts`; none for uk/ja/ko/zh/id/hi) run in a module Web Worker from the `blacktop-pilot-voice` Cache Storage (voice from Hugging Face, ONNX Runtime from cdnjs, phonemiser from jsDelivr; opt-in from Settings, ~50-90 MB), played through `playRadioVoice` (a narrow boom-mic band and drive before the shared chain), with the roger beep at the end. Phrases are cached; the worker starts with a ride or radio-style guidance and stops after 10 idle minutes. If it isn't downloaded or can't make a call in time, the phone's voice says it: a male system voice where the phone names one (`MALE_VOICE` in `lib/speech.ts`), pitched down otherwise, only wrapped in squelch (Web Speech output can't be filtered). Workers build as ES modules (`worker.format` in `vite.config.ts`). Convoy voice chat and Blacktop Radio music stay clean. The one AudioContext is unlocked on the first tap and suspended except while a sound plays (or while the anti-theft alarm is armed, `holdAudio`); don't create others for effects.

### Battery

The screen stays on for a whole ride, so anything that runs per frame, per sensor event or per GPS fix is multiplied by hours. Rules that keep a ride cheap:

- Ride state (`useActiveRide`) is saved at most every 10 s, straight away on start/pause/resume/end and when the app goes to the background; lean/G-force samples are stored packed and appended in place. Never go back to serialising the whole ride on every change.
- Sensors: `useLeanAngle(active, displayIntervalMs)` and `useGForce(active, { display, displayIntervalMs, onSample })` sample at full rate but only re-render at the display interval, and G-force not at all unless the gauge is shown; crash detection is fed through `onSample` and runs its stop-window check on its own timer.
- The live overlay recorder (1080p canvas + MediaRecorder) only runs when `rideOverlayEnabled` is on, and draws at 30 fps. Its mini map (`lib/overlayMiniMapGL`) is a hidden MapLibre map in the Blacktop dark style copied into a circular heading-up dial, loaded on demand on the first fix of a recording (the old OSM-tile renderer in `lib/overlayMiniMap` draws until it has a frame).
- The nearby-riders ring on the map is a faint dashed outline, shown only while stopped and not guiding (no fill, no pulse).
- The backdrop wordmark is one WebGL quad (`lib/backdropGL.ts`), drawn ~30 fps while it only drifts and ~20 fps flat (no lens) on the ride screens; it stops while the map covers it or the page is hidden. Never go back to an SVG/CSS filter over a full-screen moving layer: the browser redraws those on the CPU every frame, and every frosted card above re-blurs with it (it was the app's main source of lag).
- Maps render at `MAP_PIXEL_RATIO` (at most 2x, from `lib/maplibreWorker`; pass it to every `new maplibregl.Map`), and nothing blurs over the map (`.map-shell` in index.css drops backdrop-filter for more opaque panels).
- The Home globe draws ~30 fps at 2x and stops while off screen. Heavy libraries load on use: the QR scanner via `loadQrScanner()` (never import html5-qrcode's class statically), the receipt image via `import('html-to-image')`; `lib/validation.ts` is a tiny zod-free checker.
- The map overlay stays mounted after its first open: `BlacktopMap` only watches GPS while visible or guiding, does no camera work while hidden, and skips the follow animation when the rider hasn't moved or turned.

### Ride tracking domain model

Core ride/convoy types live in `src/types/blacktop.ts` (`RideSession`, `GpsPoint`, `LeanSample`, `ActiveRideState`, `RideStats`, badges) and `src/types/convoy.ts` (`ConvoyState`, `ConvoyMemberInfo`, waypoints, `calculateBadges`). A `RideSession` accumulates GPS points and (optionally) 10Hz lean-angle samples for crash detection and lean-angle visualization; convoy badges (Speed Demon, Journeyman, Lean Fiend, G-Lock, Corner Carver, Fallback) are computed client-side from member stats via `calculateBadges`; solo threshold badges (Night Owl, Hard Ass, Always Out) come from `soloBadgesForRide`. Both are banked in the badge wallet (`ride/lib/badgeWallet.ts`). The receipt reports convoy badges after `endRide()` has reset ride state, so `ActiveRide` gates saving them on the captured `finalMembers`, not `rideState.isConvoyMode`. Badge display is filtered by the rider's setup (`experience/lib/badges.ts`).

G-force is shown app-wide as a friction circle (`components/GForceCircle`, and `lib/gForceCircleCanvas` for the overlay video: keep them in step): peak envelope per direction, peak left / right / braking / acceleration, live dot, auto scale (1 / 1.5 / 2 / 3 G). `lib/gForceVector` works out vehicle-frame lateral / longitudinal G with gravity removed (axes from gravity and the screen's right edge, so any mount or orientation works); for vehicles that lean, cornering G is tan(lean) since a leaning bike's phone barely feels sideways force. Rides store `gEnvelope` / `gMax` (merged on restore) and the receipt shows the traced circle in ink. The older total-magnitude value (`currentG` / `maxGForce` / `gForceSamples`, ~1.0 at rest) still drives crash detection, the G graph and the G-Lock badge; Track Day telemetry uses the gravity-free magnitude.

Crash/rescue flow: `useCrashDetection` (ride feature) watches device motion + speed to detect a crash, surfaces a confirmation prompt, and on confirmation/timeout calls into `useRescue` (rescue feature). `rescue_request` goes over the convoy's realtime channel to every member (membership checked server-side before it's shown): everyone gets the `RescueAlert` card and a burn-coloured rescue route on the map (`rescueBridge` → `BlacktopMap`). Any member can answer with "I'm on my way" (`rescue_responding`), which names them to the rider in distress (persistent banner on the ride screen) and to the convoy; the leader's "Add Waypoint" sends `rescue_acknowledged`. Rescue also notifies Discord (`discord-announce-*` Edge Functions) and push (`send-push` `{action:'rescue'}`). Who a call reaches is the rider's choice (Settings → Safety: convoy, crew, Discord, riders nearby within 5–50 km); every send path goes through `rescue/lib/reach.ts` (`rescueReach(settings)`). The one path that needs no server is the emergency contact (Settings → Safety, `emergencyContactName` / `emergencyContactPhone`, kept on the phone): `EmergencyTextButton` on the crash screen and the rescue banner, and `emergencyTextAction` on the solo rescue toasts, open an `sms:` text from the phone's own messages app with a maps link (and the what3words, when known). Crash detection can only be switched on through `requestAutoRescueConsent()` (rescue feature; `AutoRescueConsentDialog` in App.tsx): the rider must tick that Blacktop isn't an emergency service before "Turn on" works, the acceptance time is saved as `autoRescueAcknowledgedAt`, and anyone with it on but never accepted is asked once on launch (declining turns it off). Every enable path (Settings, the Home safety card, the setup deck, the Your Blacktop list) awaits it. The rescue drill (`RescueDrillButton`, in Settings → Safety and the Home safety sheet, which closes itself first; the screens run from `RescueDrillHost` in App.tsx via `lib/drillStore`, outside every sheet: portaled out of a Radix sheet, they were untappable and closed the sheet, drill and all) plays the real crash check on a 15 s countdown labelled as a drill, sends nothing and sounds no siren, then checks crash detection, motion sensors, location and notifications and lists who a real call would reach; The notice (`rescueDisclaimer()`, `RescueDisclaimer`) is shown only in that dialog, not as a standing note in Settings or onboarding; the Terms (Rescue & crash detection, Anti-theft alarm, Public Road Privacy) and Privacy Policy repeat it, so keep them in step when these features change. "Riders nearby" reaches devices that opted in to the `rescue_nearby` push category, which keeps their position rounded to 0.1° like weather alerts (`register_push_subscription`, migration `20261001100000_rescue_nearby.sql`).

### Public Road Privacy (Settings → Privacy → "Log Peak Speed & Gs")

Off (`logPeakTelemetry: false`): every peak (top speed, max lean, peak G) reads `PEAK_HIDDEN` ("--") app-wide via `usePeaksHidden()` (ride feature): the ride screen's Max, lean bar max (`hideMax`) and G circle figures (`hidePeaks`), receipts (except Track Day receipts), history, ride detail (and its corner report), stats, Home, garage, logbook and vehicle cards. ### Anti-theft alarm (`src/features/alarm`)

A pattern lock and motion alarm for a parked vehicle. `armAlarm()` runs from a tap (iOS grants motion access and starts audio only from one), pauses a running ride (unlocking never resumes it; the rider presses play) and shows `AlarmOverlay` (mounted once in `App.tsx`, above everything, the map included): solid black, a big red lock on the top half (left half in landscape) and an Android-style 3×3 pattern pad (`PatternLock`; a dot jumped over in a straight line joins). The first arm asks for a pattern twice (at least 4 dots; only a hash is kept, `blacktop_alarm_pattern`). A 5 s exit delay learns the resting position, then `useTamperSensors` (the alarm's own orientation + motion wrapper; works with the phone any way up, unlike ride lean) feeds `TamperDetector` (`lib/detector.ts`, sensitivity from `alarmSensitivity`): a small sustained tilt or two-window jolt chirps a warning; a big tilt, a hard jolt or three warnings in 30 s start a 7 s entry delay of beeps, then the siren (`alarmSiren`, straight to the speaker behind a limiter) until the pattern is drawn. Wrong patterns while armed: two warnings, the third sets the siren off. The armed state is never saved, so closing the app unlocks it; the wake lock and the audio context (`holdAudio`) are held while the lock is up.

- Arm buttons (`AlarmButton`, map `AlarmControl`): Home header beside the rescue card; ride screen left of the live speed in landscape, its own row above the controls in portrait; the map's right-hand controls under the compass. The first tap sets the pattern.
- The overlay is portaled to `<body>` at z-10000: `#root` is its own stacking context (view transition), so anything else portaled to body (dialogs, the radio bubble) would sit on top.
- Sounds go through `lib/alarmSound.ts`: in the Android app the native `AlarmSound` plugin (`AlarmSoundPlugin.java`) plays the siren and chirps on the built-in speaker (never a Bluetooth headset or intercom), with the alarm volume at full and out of call mode while the siren sounds, and pins the screen (`startLockTask`) from arming until unlocked. The iOS twin is `ios/App/App/AlarmSoundPlugin.swift`, registered in `MainViewController.swift` (iOS has no pinning); builds without the plugin and the browser fall back to Web Audio.
- Auto-rescue (crash check timeout or its Send rescue, never the manual rescue button) calls `startRescueSiren()`: phase `rescue`, the siren and a "Crash detected" screen anyone can stop.

### Burn

Burn must remove everything. Server: `burn-account` deletes the auth user (user columns cascade from `auth.users`; new tables must too), plus what doesn't cascade: card photos in storage (`card-photos/<uid>/`), `edge_rate_limits`, and rows whose link is `ON DELETE SET NULL` and would keep a location (`blacktank_places` by `set_by`, `convoys` by `leader_id`, which cascades to members / waypoints / messages), with `world_locations` deleted explicitly too; any of those failing stops the burn so it can be retried. Retention (migration `20261001001636_c14bbe5c….sql`, pg_cron): `world_locations` rows not refreshed for 15 minutes go every 10 minutes, and convoys that are inactive (a leader leaving only deactivates one; nothing ever reactivates a convoy) or over 24 h old with no member heard from for 16 h are ended hourly. ### Card Wars (`src/features/card-wars`, `/arcade/card-wars`)

A card battler in the Arcade (needs `blacktopWorldEnabled` and `collectiblesEnabled`). A deck is five cards (real cars and bikes) and three dog tags, each a different power, chosen from the four there are (`TAG_SLOTS`; which one stays at home is the player's call). The band stands still in Thermal mode and with reduced motion.
- Page changes are Blacktop's pixel warp (`lib/warp.ts`): a small canvas scaled up without smoothing, owned by that module and drawn outside React so it's on screen in the same instant a change starts. The old page turns to block pixels (`snapshot`: one pass over what's on screen: box fills and outlines, text as bars, icons as blocks, pictures and 2D canvases copied across; no library) and draws back from where the rider tapped; the next page takes its place underneath; the old pixels fade into a copy of the new page, which closes back in, getting finer, until it matches and lets go. `installWarpNavigation()` (App, before the router mounts) starts the quick one on every change of address by hooking `history.pushState` and `popstate`, which fire while the old page is still there to copy; redirects (replace) and same-page changes are left alone. Home and Blacktop World swap at the unhurried pace: Home's globe calls `startWarp` itself and changes the route at `WARP_SWITCH_MS`, and World back to Home is slow too. `RouteReady` (inside the routes' Suspense, so it runs once the page has really loaded) calls `endWarp()`; a failsafe lets go regardless. While a warp is up `PageTransition` adds no slide of its own (the `page-in-*` classes are only for Thermal mode and reduced motion now, where the warp doesn't run). World hands back to Home with a `replace`, which the history hook treats as a page change (other replaces are redirects and get none). The map opening or closing isn't an address change, so the overlay store starts the quick warp itself (`warpFromTap` in `openBlacktopMap` / `closeBlacktopMap`).
- Pared-back Home (solo only, Track Pack off: Start, Plan a Route, Track Day and the globe): Start begins the ride straight away (`/ride`, free ride), Plan a Route opens the solo lobby, Track Day opens `/track`, the globe opens the map. Track Day always shows here; on the full Home it follows `trackPackEnabled`.

### Translations (`src/lib/i18n`)

18 languages (English + `LANGUAGES` in `lib/i18n/index.ts`); the picker is on the BT logo in Settings. The English text is the key: `tr("Join Convoy")`, with `{0}`, `{1}` filled from params (`tr("{0} rides", [n])`). Dictionaries are `lib/i18n/locales/<code>.json`, loaded before the app is imported (so module-level data can call `tr()`); a missing entry falls back to English. `vite build` ships each in two chunks (`scripts/i18n/vite-split.mjs`, `virtual:i18n-dicts`): `main`, loaded before the app starts, and `extra`, the text only used by the files in its `EXTRA` list (Terms, Privacy, the demo tour and its scenes, the Enterprise demos; about a third of each language), loaded by `loadLocaleExtra()`, which those pages' `lazyPage` loaders await (and the idle prefetch runs). Strings no code uses aren't shipped. A string goes to `extra` only if every literal use of it is in an extra file, so anything else stays in `main`; add a file to `EXTRA` only if nothing outside those pages renders it. Dev serves whole files. Changing language saves `blacktop_language` and reloads.

- Every user-facing string goes through `tr()`, including toasts, aria labels, errors, spoken prompts (`map/lib/navigation.ts`, `lib/speech.ts` picks a voice for the app language) and module-level copy. Never wrap classNames, colours, ids or anything sent over the network: pit board presets travel as English ids and are shown/said per phone (`track/lib/pitCalls.ts` `pitLabel`).
- Whole sentences, never fragments: no `tr("Start your")` + word, no English `'s'`/`'rider' : 'riders'` suffixes; use one key per case (`tr("1 rider")` / `tr("{0} riders", [n])`). `terms` (ride/drive, rider, vehicle nouns) are translated nouns; where ride/drive is a verb, pick between two whole sentences on `terms.car`. `lowerName()` lower-cases a name mid-sentence (not in German).
- Keep product and badge names in English (Blacktop, Blacktank, Speed Demon…), except Track Day, which has a local name per language, and Blacktop Enterprise, where everything but the words Blacktop and TrackPack is translated (keep it consistent in every string that mentions it); "Hi-vis" is never translated as police.
- Workflow: `npm run i18n:check` re-extracts `scripts/i18n/keys.json` and lists what each language is missing (`--missing de` as JSON). Translation work files are `<dir>/<lang>/*.txt` lines `N<TAB>text` (N = index in keys.json) merged with `node scripts/i18n/merge.mjs <dir>`, which rejects lines whose placeholders don't match. Re-extracting shifts the indices, so merge before changing code.

### Nimiq Pay mini app

Blacktop also runs as a Nimiq Pay mini app (a WebView inside the Nimiq Pay app; `@nimiq/mini-app-sdk`, `features/tips/lib/walletBridge.ts`: `isNimiqPayHost()`, NIM / USDT payments, `/pay`). Nimiq doesn't document what its WebView allows beyond the wallet providers, so `/device-check` (`pages/DeviceCheck.tsx`, a developer page, not linked or translated) tests every device feature the app uses (location, motion, mic, camera, wake lock, audio, speech, push, storage kept between opens) in whatever browser opens it, with a copyable report. With no saved language choice, the app follows Nimiq Pay's (`window.nimiqPay.language`, in `lib/i18n` `detect()`). Full screen (`lib/nimiqFullscreen.ts`, `components/NimiqFullscreenPrompt.tsx` mounted in App): newer Nimiq Pay hosts inject `window.nimiqPay.requestFullscreen` / `exitFullscreen` / `getFullscreen` / `onFullscreenChange` (SDK 0.2.4; we call the host directly, the installed SDK is 0.1). Nimiq requires the app to ask before every request and shows no prompt itself, so Blacktop asks once per launch ("Don't ask again" mutes it, `bt.nimiq_fullscreen_prompt`) and Settings → Your Blacktop has Go full screen (the same prompt). It ends with the host's button, Android Back or backgrounding; state is re-read on resume. Hosts without it show nothing.

### Native device integration

Capacitor plugins (`@capacitor/geolocation`, `@capacitor/filesystem`) and browser device APIs are wrapped in small hooks rather than called ad hoc: `useWakeLock` (re-takes the lock after the browser drops it, until released; held by the ride, pillion, lobby and solo lobby screens and by the map overlay during a ride or from a lobby), `useOrientationLock`, `useLeanAngle` (device orientation → lean angle), `useBackgroundAudio`, `usePictureInPicture`, `useLiveOverlayRecorder` (records a live ride overlay video, with `convertToMp4`/ffmpeg.wasm for conversion). New native-device features should follow this hook-wrapper pattern.

Permissions are asked for where they're first needed, never up front (the old Quick setup screen after onboarding is gone): location by the first ride or map, the microphone by joining voice, the camera by a QR scanner, notifications from Settings → Notifications, plus one card ever (`PushNudge`, mounted in App; `offerPushNudge` in `notifications/lib/pushNudge.ts`, which imports nothing) the first time a rider joins a crew or a convoy or turns on crash detection, and only where the phone can still be asked. Permissions stay granted across launches. The OS keeps location, microphone, camera and notifications; the app must not treat iOS's forgetfulness as a revoke. iOS web apps report location as "prompt" again after closing, so anything that gets a fix calls `noteLocationGranted()` (`lib/locationGrant.ts`) and the Home safety card only shows rescue as paused for "prompt" when location was never allowed on the phone. iOS also forgets motion / orientation access (crash detection, lean, G, the alarm) and only asks from a tap: every request goes through or notes `lib/motionPermission.ts` (`requestMotionAccess`, `noteMotionGranted`), and `installMotionRegrant()` (App.tsx) re-asks on the first tap after a relaunch, so the sensor listeners already attached start receiving again. It re-asks whenever lean, the G gauge or crash detection is switched on, not only when the phone is marked as having allowed it before (riders from older versions had no mark, and their gauges stayed dead once the old permissions screen went); a rider who refuses is left alone for a week. Anything meant to be held down on a phone takes the `hold-target` class (no text selection, no callout, `touch-action: none`): without it an iPhone selected the lettering on Home's globe and cancelled the hold.

### UI layer

shadcn/ui components (generated into `src/components/ui`, configured via `components.json`) plus Tailwind (`tailwind.config.ts`, near-black neutral palette in `src/index.css`). Path alias `@/*` maps to `src/*` (configured in both `vite.config.ts` and `tsconfig.app.json`) — use it instead of relative `../../` imports.

- Backdrop: `components/AppBackdrop.tsx` is mounted once in `App.tsx` behind every screen: slow "lava" accent blobs, a tightly packed `BLACKTOP` wordmark in the background colour (only the blobs' light reveals it) seen through a fish-eye lens larger than the viewport, all drawn by one WebGL shader (`lib/backdropGL.ts`: rows, belts, lens and pull bulge per pixel; plain CSS rows without a lens where WebGL is missing), and a mist layer. Each wordmark row is a slow conveyor belt (alternate rows run opposite ways), and the rows form an endless vertical loop that follows any scroll in the app (window or inner scrollers) through the lens. `lib/backdropMotion.ts` drives it all from one rAF loop feeding the shader: `surgeBackdrop(strength)` spins the belts up and lets them coast back (`BackdropHost` in `App.tsx` calls it on taps of interactive elements and on route changes), `scrollBackdrop` moves the rows, and `setBackdropPull` is used by `components/PullToRefresh` (app-wide, touch only: rows follow the finger, belts slow, the lens bulges; release past the threshold refetches active react-query queries and fires `blacktop:refresh` on window; mark areas `data-no-pull` to opt out). While the map loads, the backdrop moves in front of the page as the loading screen (belts at a fast cruise, `setBackdropCruise`) and pauses once the map has drawn. On the ride and pillion screens the backdrop runs `flat` (no lens, fewer frames, with the screen on all ride), and the belts cruise faster past the amber speed threshold and faster again past red (`BackdropHost` reads `useRideSpeed`). Don't call `useActiveRide` app-wide: it resumes GPS for a restored ride (`useRideSpeed` is the side-effect-free read). Pull-to-refresh is off on the ride screen and the map. Page roots must not paint an opaque background.
- Frost: any `bg-card*` surface is frosted automatically (a global rule in `index.css`; opt out with `.no-frost`). Overlays (dialogs, sheets, menus, selects, tooltips, toasts), outline/secondary buttons and header buttons use `.frost-accent` (frost + thin accent border + accent icons). Primary CTAs stay solid.
- Screens use `components/PageHeader` (`PageHeader`, `HeaderButton`) for their header. Settings sections are `settings/components/CollapsibleSection` tiles in a two-column grid; pass `index` so an opened section drops down full width under its row (tiles never move, no half-empty rows).
- Safe areas (notch / Dynamic Island, home bar, rounded corners; the sides too in landscape). Read them only through `--safe-top` / `--safe-right` / `--safe-bottom` / `--safe-left` (`index.css`, set from `env()`), never `env(safe-area-inset-*)` itself: one source, and a notch can be tried in a desktop browser (`document.documentElement.style.setProperty('--safe-top', '59px')`; iPhone 16: 59 top / 34 bottom in portrait, 59 left and right / 21 bottom in landscape). Pages: every route sits in `PageTransition`'s `.page-safe-x` (the sides), and the page root takes `safe-top safe-bottom` (doubled selectors, so `landscape:p-3` / `md:p-5` on the same element can't undo them, which used to leave the last row under the home bar in landscape). Full-screen overlays (`fixed inset-0`): `safe-frame` (a transparent border as wide as the safe area: the background still fills the screen while content, padding and absolutely placed children stay inside), or `safe-frame-x` when it already has `safe-top` / `safe-bottom`; not on one whose child must fill the screen (a map), where each edge-pinned control adds the inset itself (`bottom-[calc(0.75rem+var(--safe-bottom))]`, as the map's panels and close button do). Their inner card gets `max-h-full overflow-y-auto`, and a column that may be taller than the screen centres with auto margins, never `justify-center` (that cuts the top off for good: the ride receipt). Dialogs and sheets (`components/ui`) carry `dialog-fit` / `sheet-*` (never wider or taller than the safe area, scroll on a short screen, close button with a thumb-sized hit area); toasts sit below the notch (`ui/sonner.tsx` offsets). Anything shown while riding must also fit a phone in landscape (`short:`): the crash check puts its two answers side by side there. Check new screens at 320×568, 568×320 and with the insets above.
- Glove-sized targets: `.touch-target` is 48px minimum, and `.glove-hit` adds an invisible 48x48 hit area round a control that has to look small. `.tall-hit` does the same in height only, for controls packed side by side (the halves of a switch, pagination dots). Anything used while riding (ride controls, turn banner, hazard report, rescue, alarm, map controls) must be at least 48px to press.
- Numbers use `.font-mono`, which is Inter with tabular figures (not a monospace stack). Page changes (the pixel warp, see Personalisation → Home's globe), `.pressable`, `.stagger-in` and skeletons (`components/skeletons.tsx`) are the shared motion primitives; all respect `prefers-reduced-motion`.
- Burn UI uses the fixed `--burn` colour, never the accent. The anti-theft lock is burn orange wherever it appears (Home, the ride screen, the map control, the alarm screen, the pattern dialog), and so is the north half of the map's compass needle (south is grey; `blacktopMap.css` redraws MapLibre's needle).
- Colour roles (home screen and new UI): icons in the accent colour, headings white (`text-foreground`), subheadings grey (`text-muted-foreground`).
